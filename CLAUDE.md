# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

There is no build, lint, or test tooling here, apart from the generator for the private UNED search page (see below). The git repo pushes to the public https://github.com/alcaloide2000/Egypt (branch `main`). ### UNED transcript search

`private/buscar-curso-uned.html` searches the five UNED class transcriptions, the mind map, the Spanish half of the Curso UNED tab and the five `curso-uned-clase-N.html` pages (each hit there links to its `<section id>`). It is modelled on the `/buscar` page of the user's `economia` project: accent- and case-insensitive phrase search, results grouped per class, and each transcript hit's `¶ N` tag expands the full paragraph. Each class result also links to its recording and its "en detalle" page.

- **Build**: `python scripts/build_uned_search.py` fills `scripts/uned-search.tpl.html` with the data and writes the page. Rebuild after changing the mind map, the tab or a class page. The recordings' INTECCA links live in `VIDEO_URLS` in the script; when the user pastes one, turn any `&amp;` into `&`.
- **Sources**: the transcripts are `private/uned/clase-1.txt` … `clase-5.txt`, extracted from the session where the user pasted them. `curso-uned-transcripciones.pdf` (repo root, 115 pages) is the same text as a PDF; it was made once with a throwaway reportlab script, not a repo script.
- **Privacy**: `private/` and the PDF are gitignored. They hold the lecturer's full talks and the repo is public, so never commit them or publish them anywhere public. The script and template contain no transcript text and are committed.
- **Published copy**: the page is also a **private** artifact, https://claude.ai/artifact/TT8sDZb3PYpBGQ7FEcDZC1. Republish it after every rebuild (same `file_path`, or that `url`), and never change its sharing. The Curso UNED tab links to it from its masthead in both languages, so other visitors see the link but can't open it. Its links point at the published claude.ai pages, not local files. In the artifact, the `?q=` search in the address is not kept (only plain `#anchors` reach the page); it works in the local copy.

### Syncing with the published artifact

The live version is the claude.ai artifact **"Ancient Egypt History Main Points"** at https://claude.ai/artifact/5LEkwRrpG4KFAx377J5y7k. It is also edited from a separate Claude Code cloud session, so it can get ahead of the local file.

- **Pull** with Artifact `action: "read"` on that URL, then copy the saved HTML over `artifacts/ancient-egypt-history-main-points.html`. Put a dated copy of the old file in `artifacts/backup/` first.
- **Push** with Artifact `publish`, using `url` set to that link and `file_path` set to the local file. Always pull and merge before pushing, because publishing over a newer live version would discard the cloud session's work. The Artifact tool only accepts the publish once the pulled version has been read in full (every line of the saved file, about 10,400 lines, in chunks of ~600), so budget for that. After that, small changes can go as `edits` on the publish call.
- When the live page and the local file differ only in the first wrapper line, there is nothing to merge. Back-up names use the date plus a letter for repeats on the same day (`…2026-10-18.html`, `…2026-10-18b.html`).
- The cloud session also commits to GitHub, so `git fetch` before pushing. If `origin/main` has moved, rebase onto it. Drop a local "pull from live" commit when GitHub already has the same page, and keep both sides when CLAUDE.md conflicts.

**Shared copy for friends.** Friends who open the main artifact's link see a pinned earlier version (before the tabs), and the owner could not find how to update it. So the current page is also published as a separate copy, https://claude.ai/artifact/MRtoicco5UtFk4gCLzrzve, which the owner shared by link on 19 Nov 2026; it works for friends and its viewers see updates immediately. After publishing a change to the main page, republish the same HTML to that copy too (Artifact `publish` with that `url` and a copy of `artifacts/ancient-egypt-history-main-points.html`), and remind the owner that the shared link may need re-sharing if friends see an old version.

The saved files begin with a publish-time wrapper (`<!doctype html><html><head>…<body>`) followed by the authored `<title>`/`<style>`. Edit the authored content, not the wrapper.

## Architecture of the main page

It is one large file (~10,400 lines, 108 info cards): inline CSS, inline SVG and three small scripts at the end (card search; tabs, hash routing and the UNED language switch; the tour slideshow). External loads are limited to Google Fonts (Fraunces, Public Sans, IBM Plex Mono). Images can't be loaded, so every "picture" is a hand-drawn inline SVG illustration.

The page has five tabs (`.tabs` bar at the top of `.page`). Between the tour and Cairo tabs sits **Photo diary** (`#panel-diary`, opened by `#diary`): an entrance to the separate photo diary artifact, with an "Open the photo diary" button and one `.diary-day` card per tour day (stops plus a "Photos and videos of Day N" link to the diary's `#day-N`, which the diary scrolls to); a small script marks today's card (`.is-today`). It cannot show the photos themselves, which live in the diary artifact's own storage. The fourth, **Visitas en El Cairo** (`#panel-cairo`, opened by `#cairo`), summarises the three-day Cairo draft plan and links to the `cairo-visitas.html` artifact. The fifth, **Curso UNED** (`#panel-uned`, opened by `#uned`), summarises the user's five-class online course on Egyptian history (UNED Tudela, spring 2025) from transcriptions they pasted; it holds summary notes only, never the transcript text, and has a box correcting the lecturer's factual slips, plus the course bibliography (`#uned-biblio-en` / `#uned-biblio-es`, each title linked to a Google Books search). The masthead links to the mind map, the private transcript search and the bibliography. Each class card ends with two `.wiki-link`s: its INTECCA recording ("▶ Vídeo de la clase N (UNED)" / "▶ Class N recording (UNED)") and its "en detalle" page. It has an English/Español switch (`#unedLang`): the two versions are sibling `[data-lang]` blocks, so a change to one must be made in the other too. The temple guide pages (Abu Simbel, Philae, Kom Ombo and Edfu, English and Spanish) are linked from the Main points masthead ("Temple guides for the tour"), from the matching tour day cards and Photo diary cards, and from the Abu Simbel, Philae, Ptolemy VI and Ptolemy III (Edfu) info cards; the Cairo days card links the pyramid page. Add each new temple page in all of those places. The first two are **Main points** (`#panel-main`: masthead, search, map, cards, timeline) and **Private Alimaña Tour** (`#panel-tour`: the user's trip, 18–28 Nov 2026: flight Madrid → Cairo and a night at the Prime Boutique Hotel Heliopolis Terrace in Cairo, a night at the Aswan Nile Palace on the 19th, the booked C La Vie Aswan–Luxor program, a night at the Aracan Eatabe Luxor Hotel on the 23rd, a night flight Luxor → Cairo on the 24th, three days with their guide Omarcel (a day trip to Alexandria on the 25th, then Saqqara, Giza and Islamic Cairo; draft plan) and the flight home on the 28th, as `.day-card`s). Above the day cards sits `#tourShow`, an auto-playing slideshow (11 slides, the Alexandria day trip among them, with inline SVG art and a route bar whose boat moves per slide); its script pauses it while the tab is hidden. Below the day cards, `.tour-time` ("The tour through time") lists every tour place in the order it was built: a scrollable SVG strip from 3500 BC to AD 2025 with one dot per place, then an `ol.tt-list` grouped by era, each item with a day chip in that day's accent (Cairo draft-plan stops get a dashed chip). Keep it in step with the day cards and the Cairo plan. Tour stops link to `#card-<slug>`; a second small script at the end switches to the tab holding a hash target, and `#tour` opens the tour tab. Don't give tour content the `info-card` class or the search will count it.

Adding a site usually means touching **four places** that must stay consistent:

1. **Map marker**: a `<g class="site-marker" transform="translate(x,y)">` inside the map `<svg viewBox="0 0 600 860">`. It has a glyph plus `<text>` label and sub-label. Pyramids get triangle/step glyphs, people and temples get other shapes. Crowded clusters (Cairo–Giza–Saqqara corridor, Theban west bank) have been hand-respaced to stop labels overlapping.
2. **Hover illustration**: a `<button class="hotspot">` plus a `<div class="tooltip" id="…Tooltip">` holding an `<svg class="illustration" viewBox="0 0 100 128">`. Both are absolutely positioned with `left`/`top` percentages equal to the marker's map coordinates (`left = x/600`, `top = y/860`; Giza `translate(240,200)` → `left: 40%; top: 23.26%`). Colour comes from `style="--accent: var(--…)"` through one shared tooltip CSS system. Don't add per-site tooltip CSS.
3. **Info card**: `<div class="info-card" id="card-<slug>">`. Sites with no known findspot (Palermo Stone, Mentuhotep I, Netjerkare Siptah) and rulers with no monument in Egypt (Xerxes I, Artaxerxes I, Artaxerxes II, Darius III, Ptolemy VII, Ptolemy IX, Ptolemy X, Ptolemy XI, Ptolemy XIV) use `class="info-card unlocated"` (dashed style) and get no map pin. A card can be singled out with `class="info-card featured"` plus `--accent`, which tints its background with that accent (Djoser's card uses indigo, and so does the shared Pepi I & II card, `#card-pepi`, for Pepi II). The same idea in lists is `.is-featured` with a `--hl` colour (a timeline legend chip and a tour-timeline row for Djoser), and `path.tl-highlight` draws a soft indigo halo behind a timeline entry (Pepi II has one behind his bar and one behind his name in the "Unas → Pepi I → Pepi II → Ibi" label, plus a featured legend chip). Cards link to Wikipedia ("Read on Wikipedia ↗"). Alternate and ancient names (e.g. Abedyu for Abydos, Khnum-Khufu/Cheops for Khufu) go on the existing card rather than in a duplicate entry.
4. **Timeline entry**: inside the timeline `<svg viewBox="0 0 3097 1000">`. The axis is broken (`<g class="tl-break">` marks the gaps) into segments. Labelled `<rect>` era bands with a `tl-era-label` mark Predynastic, Early Dynastic & Old Kingdom, New Kingdom, 25th and 26th Dynasty (one segment, c. 760–323 BC: Piye, Shabaka, Taharqa, Tantamani, Psamtik I, Necho II, Psamtik II, Ahmose II, then a PERSIAN band for Cambyses II, Darius I, Xerxes I, Artaxerxes I, Darius II and Artaxerxes II, then a 30TH DYN. band for Nectanebo I and Nectanebo II, a short unlabelled Persian sliver for Artaxerxes III and Darius III, and a last sliver for Alexander the Great), Ptolemaic (Ptolemy I–XV, Cleopatra VII, Philae, the Serapeum, Dendera) and Kush. The Middle Kingdom segment has a highlighted indigo band (`rect.tl-era-mk`, from Mentuhotep II at x 1008 to the break after Senusret III, with an indigo `MIDDLE KINGDOM` label and a "c. 2055–1650 BC" date inside it, plus a featured legend chip); the Second Intermediate segment has no band. Single-monument entries are wrapped in `<a href="#card-<slug>" class="tl-link">` so clicking one jumps to its card (`.info-card:target` flashes gold). Composite entries stay unlinked. Conventions: reigns and construction spans are bars, buildings are solid markers, and deaths are hollow dashed markers. Entries that span too many dynasties (e.g. Tombs of the Nobles) get no timeline mark.

When the timeline changes, also update the long `<desc id="tlDesc">` prose so it stays accurate. The masthead/timeline `.lede` text should describe the whole page.

### Theming

All colours are CSS custom properties on `:root`. Each one is defined three times: light defaults, `@media (prefers-color-scheme: dark) :root:not([data-theme="light"])`, and `:root[data-theme="dark"]`. A new colour must be added in **all three blocks**; a missing `--lapis` once broke dark mode. Dark mode uses warm grey (`#302f2c` / `#3a3936`), not black. Each site family has its own accent (ochre, gold, lapis, malachite, indigo, rose, solar, turquoise, kush, persia…).

### Search script

The `<script>` at the bottom filters `.info-card` elements by full-text match and wraps hits in `<mark class="hit">` using safe DOM text nodes (no innerHTML). It dims non-matching `.site-marker` groups and scrolls to the first match. New cards and markers are picked up automatically as long as they use those classes. A card can carry a `<button class="highlight-btn" data-highlight="…">` (Djoser's does) that fills the search with that word, so the matching markers stay lit and the rest dim; give related markers a `<title>` with the ruler's names (e.g. Djoser, Netjerikhet) so every name finds them.

## Working conventions

- Check for overlapping text after any change to the map or timeline. Most past bugs were label collisions or labels placed at the wrong date (e.g. Thutmose III's label had drifted ~130 years off). Render the page and check bounding boxes or a screenshot.
- Historical claims should be accurate and dated "c. … BC". When a name is ambiguous (which Thutmose, which Mentuhotep, a misspelled site), clarify or confirm before adding it.
- The user writes short, often misspelled or Spanish-influenced requests (e.g. "ajetaton" = Akhenaten, "nejen" = Nekhen). Work out what they mean, and check whether the item already exists on the page before adding it.
